# Billing Workflows

All billing graphs are defined in code in `.seeds/billing/` (registry `billingGraphs` in `index.ts`, one file per area: `facts`, `service`, `charges`, `claim`, `checks`, `facility`, `documents`, `discovery`, `intake`, `cycle`, `payer-files`, `recovery`, `schedules`, `accounting`) and seeded as system graphs, in dependency order. Every billing decision is a small **rule** graph drawn on the canvas: conditions that read as sentences, ordered first-that-applies choices, logic gates, rules run per item and combiners. Shared **tables** hold only reference data an agency edits as rows: code sets, code labels, limits and settings, and pure code mappings. **Stages** sequence rules, actions and tasks; **workflows** react to an event. Code nodes only read and write (facts, storage, X12, the model) and never decide. Every pin and exit of every seeded graph has a Title Case label and a description: the seed runs `documentationIssues` next to `validateGraph` and fails on either. Pins the glossary (`.seeds/billing/glossary.ts`) knows are documented once there.

## Workflows and what starts them

One workflow per event or long-lived process; every piece of it is a stage or rule it calls. A claim goes to a payer one way (**Submit to Payer**), is corrected one way (**Correct Claim**) and every payment is classified and routed one way (**Route Remittance**, for 835 claim payments and hand-posted payments alike).

Insurance discovery emits no event of its own: the coverage it adds is checked by Check Eligibility, whose 271 emits `eligibility.answered`, and its History `discovery` only tells the claim cycle discovery was tried.

The other starts stay direct, because the person asking waits on the run they start: an import (its run is the import's progress), Start Task and Check Eligibility on a claim, Restart Payer Cycle, and the runs graphs start for each line, deadline or report. Recover Draft and Recover Claim Cycle are started by the worker when a run fails or is cancelled.

| Fix Claim               | `billing.fix-claim`               | Cycle Claim, Review Claim, Submit to Payer, Correct Claim                            |

Review Payer File Line and Deadline Reminder stay workflows: each runs once per line or deadline beside the run that spawned it, so a payer file and the morning deadline run finish without waiting on billers (and Watch Deadlines finds the reminders it already opened by their runs). Recover Draft stays a workflow the worker starts, as a failed or cancelled run cannot go on to an exit of its own. Work Denial, Refund Overpayment and Discover Insurance stay child runs of the cycle (Discover Insurance is also a Start Task): Watch Deadlines names a due task by the workflow of its run (Task Deadline Kinds table: Work Denial: appeal, Log Records Request: records, Refund Overpayment: refund).

## Intake: PCR received to Ready for review

The encounter (the imported report) is never changed; every PCR gets exactly one claim, so the claim's history is the audit trail of what became of it. Nothing about the patient, payers or service is worked until the trip is classified, and a not-billable trip is voided right away with its reason on the history. Reports are often fragmented, so the rules trust only what a report always has (NV/PN values read as missing) and send a biller only the reports too incomplete or contradictory to classify.

Every decision is logged on the claim history as a `decided` event: a rule's decision (classification, patient, payers, service, each change of status with the Next Claim Step reason) by **Record Decision** or the store, logged as automatic; and every task a biller completes on the claim, with who, the outcome, the values they set and an optional note, logged by the API in the same transaction that completes the task, so an overridden graph cannot leave a decision out.

```
read report → open draft claim (logs `opened`)
├ duplicate → Review Updated PCR (maps the facts, classifies) → Work the Claim Again | close
└ Work Draft Claim
   ├ Map Encounter Facts
   ├ Decide Whether to Claim: Classification → Classification Needs Review
   │    clear → logged (billable: Classified as …, not billable: no claim) · doubtful → task Review classification
   ├ Record Classification on the draft; not billable → Void (the history says why)
   ├ Read Narrative Findings (local model, with quotes)
   ├ Claim Patient (match, confirm, assign, log how the patient was found)
   ├ Determine Payers: Match Payer Directory → Medicare Secondary Payer → Coordination Order → Agency Payer Rules → log the billing order
   └ Bill the Claim
      ├ Determine Service: Emergency | Scheduled | Treat No Transport | Refusal → Deceased Handling (QL) → Agency Service
      │    each: Base Service = Level of Service + Emergency Status + Loaded Miles + Non-Covered Miles
      ├ Review PCR (coding review task, every reason shown) → log the service billed and why
      ├ Build Claim: Assign Charges → Assign Claim Properties → Agency Claim Rules → Save → Check Eligibility
      ├ Decide Responsibility: Facility Responsibility on the saved claim
      │    facility → Bill Facility (task Bill facility: bill the facility → claims.facility_id, or bill the payers)
      ├ Fix Claim (payers): Check Claim → Fix Claim Data task → Patch → Reprice Triggers → Reprice Claim
      └ Start Payer Cycle (a facility claim waits on the facility step for its invoice, no 837P)
```

### Checks

`Claim Issues` (`billing.claim-issues`) runs every check rule on the **Check Facts** (`billing.check-facts`, worked out by the **Claim Check Facts** rule `billing.claim-check-facts` from the Claim Record that `billing.read-claim` loads as stored, including the date math: days a certification was signed before the trip and days left to file, from the Federal Filing Limits table). Each check returns issues `{ code, field, message, coverageId }`; the **Check Severity** lookup table (`billing.check-severity`) gives each code its severity (`blocking`, `warning` or `off`; a code not listed blocks), so an agency downgrades, upgrades or turns off a check with one row. An agency adds or drops a check by overriding Claim Issues. The Fix Claim Data form asks the fields each issue's `field` names.

Each check is drawn, not written: a **Condition** per issue reads as a sentence over the Check Facts ("Transports is true and Loaded Miles is more than Likely Loaded Miles", a limit wired from the Check Limits table), an **Issue When** node holds the issue's code, field and message (a Text Template when the message names something from the claim), **Issue for Each** raises one issue per missing address part or unknown code, and Make List and Join Lists collect them. Per-payer checks run a rule for each payer: **Check One Payer** (`billing.check-one-payer`, including its filing limit) and **Check Payer Stay** (`billing.check-payer-stay`). **Rate Issue** (`billing.rate-issue`) runs for each issue to give it its Check Severity, and **Issue Matters Now** (`billing.issue-matters-now`) keeps the issues Check Claim acts on.

## Claim cycle

`Cycle Claim` loops: **Read Claim Ledger** (action, `billing.read-claim-ledger`) states where the claim stands as a typed **Claim Ledger** (balance, the payer being billed and whether it has the claim or approved it, a response waiting to be reconciled, patient approval, statements and the time since each, why the last submission was rejected). **Next Claim Step** (rule) decides the step with the **Claim Policy** table (by the kind of payer billed, its claim filing indicator or `patient`: days to wait for a payer, statements to send and days between them, collections threshold, auto-write-off limit, review required, and the write-off and collections approval thresholds), then takes the first situation that applies, each drawn as a condition (top to bottom: a credit while a payer file line waits for a biller, overpaid, work a denial, closed, reconcile, the facility still has time to pay, the facility has not paid, review, submit, await, follow up, write off within the auto-write-off limit, no payer covers the claim and insurance discovery has not been tried (no payer being billed, none answered and no `discovery` in the History; the ledger gives `payerAnswered` and `discoveryTried`), review before the patient, confirm payers, wait between statements, statement, write off under the collections threshold, else collections); its reasons give the situation that decided the step. **Record Claim Step** stores the step's status (Claim Status for the Step, an inline lookup) and continues through stale when the claim changed meanwhile. Review, submit, review before the patient and confirm payers run Check Claim first (only patient issues before billing the patient, with the last rejection on review); a blocking issue sends the claim to Fix Claim. A step the cycle has no branch for (an overridden Next Claim Step naming an unknown step) opens a `Claim step not handled` task instead of looping, and the cycle tries again once a biller retries.

The base policy (30 days, 3 statements 30 days apart, no threshold, no auto-write-off, review required, write-offs above $500 and every collections placement approved) keeps the behavior of claims that are paid; a new row for a payer kind changes it for those payers only. **Approve Closing** (`billing.approve-closing`) asks someone with `claims:approve` to approve writing off a balance above `writeOffApprovalCents` or sending one above `collectionsApprovalCents` to collections, and logs `closing_approved`; a rejection sends the claim back to the step that chose it. `facilityWaitDays` (default 60) is how long the cycle waits after a facility invoice or follow-up before asking a biller to follow up, `reviewWaitDays` (1) how long it waits before looking again while a payer file line waits for a biller, and `statusWaitDays` (1) how long a follow-up waits for the payer's 277.

A closed claim is not final. A payment, takeback (835 reversal) or refund posted to a claim closed as paid, written off or sent to collections (Medicare recouping months later, a late payer, money a collection agency recovers) posts as usual and, in the same transaction, sets the claim back to `reconcile` and logs `reopened` with why; a void claim still refuses it. The `reopened` history emits `claim.reopened`, which starts **Resume Claim Cycle** (`billing.resume-cycle`): **Restart Claim Cycle** (action, `billing.restart-cycle`, the same code as Restart Payer Cycle on the claim page) starts Cycle Claim again and links the claim to it unless a run already works the claim, and the cycle's reconcile, overpaid and workDenial steps take over. Post Payment can be started on such a closed claim for the same reason. When a Cycle Claim run fails or is cancelled while its claim is still open (not a draft, not closed) and no other run works it, the worker starts **Recover Claim Cycle** (`billing.recover-cycle`): a Claim cycle stopped task shows why, and restart starts the cycle again, while write off goes through Approve Closing (a rejection restarts the cycle) and closes the claim as written off, or paid when nothing is owed. Close Claim cancels the cycle only after closing the claim, so it never starts a recovery.

## Payer files

`Receive Payer File` reads the file first (**Read Payer File**, no writes): its kind and, for an 835, each claim payment as a **Remittance Line** with the claim and payer it matched and the facts (claim status, remark codes and crossover carrier, denied, reversal and whether the payment it reverses is posted on the claim, takeback, merged adjustments). **Route Remittance** runs for each line: **Classify Adjustments** gives each adjustment a class by its group and reason code (**Adjustment Reasons** table: a denial CARC such as CO-50, CO-22, CO-29 or CO-197 is `denial` and OA-23, the prior payer's payment and adjustments restated on a secondary 835, is `priorPayer`; neither lowers the balance), else by its group (**Adjustment Classes** table: CO and PI contractual, OA other, PR patient responsibility, and a group 5010 does not use, such as CR, unknown and sent to review). The claim counts as denied when the payer says so (CLP02 4) or pays nothing with a denial reason, as payers often report a denial as processed (CLP02 1, 2 or 3); a denied claim lowers nothing. It adds up what lowers the balance (Classes That Lower the Balance table) and takes the first route that applies, each drawn as a condition (no claim, a reversal of a posted payment, a reversal of nothing posted, a takeback, more reason codes than a payment holds, a group 5010 does not use, a payer not on the claim, a CARC in the **Claim Data Denials** code set, a CARC in the **Medical Necessity Denials** code set, a denied claim, else `reconcile`): `reconcile` posts it and the cycle asks a biller to reconcile, `reversal` posts a CLP02 22 reversal with its negative amounts when a response of the same payer has its claim number (CLP07), never more than that payer posted, `review` leaves it to a biller unposted (a reversal of nothing posted, another takeback), `unmatched` names no claim. Adjustments that would take off more than the payment leaves open are not capped: the line goes to `review` to post by hand. An 835 payer ID that matches no payer on the claim is `review`; claim order picks the coverage only when the 835 has no payer ID or several coverages share it. **Crossover Expected** (any of CLP02 19, 20 or 21, remark MA18 or N89, or a crossover carrier in NM1*TT) marks a payment the payer also forwarded to the next payer, as Medicare does through COBA; posting it logs `crossed_over` on the next payer on the claim, which counts as contacting it, so the cycle waits on that payer and follows up instead of billing it a second time. Reversals are posted before the other lines of the file, so a reversal and its corrected claim post as a pair in the same transaction. Each non-zero provider-level adjustment (PLB, such as a WO recoupment) becomes a `review` line to post by hand, on the claim whose payer claim number it references. While such a line, or any other payer file line on the claim, waits for a biller, a credit balance does not start a refund: Next Claim Step returns `awaitReview` (its first situation) and the cycle checks again daily or when the claim changes. **Post Payment** (Start Task) posts a payer payment that came outside an 835 the same way: **Payment Line** reads it as a remittance line, Route Remittance classifies its reason codes and routes it, and it is posted as routed, its reason codes deciding what is adjusted off the balance and a `denial`, `appeal` or `fix` route logging `denied` for Work Denial; a route that leaves it to a biller (`review`) refuses it with why. Patient payments and refunds post as entered. **Apply Payer File** then applies the whole file once, posting each 835 line as routed; the data layer only persists. The `denial`, `appeal` and `fix` routes post the payment and log a `denied` event the claim cycle works (Work Denial). Review Payer File Line opens only for `unmatched` and `review` lines: a rejected claim already returns to review with its own task, and an inactive coverage already blocks billing that payer. A run that applies the same file again (a retried step) gets the stored result back (`payer_files.run_id`, `source_key`), so its tasks are still created.

An 835 claim payment's service lines (2110 SVC with its CAS and REF*6R) are matched to the claim's lines by the REF*6R line number the 837P sent, else by the billed (SVC06) or paid code and charge, and stored with the response (`claim_event_lines`, `claim_event_line_adjustments`) so a later 837P to the next payer can report them in 2430. Claim-level and line-level CAS both stay in the response's adjustments, so the balance and the routing rules are unchanged; a hand-posted payment has no lines.

## Deposits and period close

**EFT reassociation** (CAQH CORE): applying an 835 stores its payment on the payer file (BPR02 amount, BPR04 method, BPR16 date, TRN02 trace number, TRN03 payer ID; a file with several 835 transactions keeps its first) and emits `remittance.file_applied`. A biller records each bank deposit on Deposits (trace number, amount, date, payer), which emits `deposit.recorded`. Either side starts a reconcile workflow that reads the unmatched pairs sharing the trace number and runs **Deposit Match** (`billing.deposit-match`): same trace number and amount → matched (`deposits.payer_file_id`), same trace number and another amount → a biller decides, else none. **Watch Deposits** asks a biller about each deposit or paying 835 still unmatched after the Days to Match, once.

**Period close:** every posting (`claim_events.posted_on`) is dated in the agency's time zone, and a database trigger moves a posting whose month is closed to the first day of the next open month, so a closed month's reports never change. **Close Period** opens a Close the month task on the first of each month with last month's totals; closing it adds the month to `accounting_periods` (Accounting Periods under Admin lists them). Reopening a closed month is not supported.

## Denials, corrections and appeals

Route Remittance posts a denial like any payment and also logs a `denied` event with its route: `fix` (Claim Data Denials: CO-4, 11, 16, 146, 181, 182), `appeal` (Medical Necessity Denials: CO-50, 56, 150, 151, 197) or `denial` (any other denied claim). While a denial waits (`denialRoute` on the ledger), Next Claim Step returns `workDenial` and the cycle runs **Work Denial** as a child run. **Correct Claim** is the one correction path: Work Denial, Reconcile Payment (resubmit corrected) and Follow Up with Payer (resubmit) all run it.

## Records requests, refunds and balance-billing protection

- **Log Records Request** (`billing.log-records-request`, from Start Task: Log Records Request, which first asks for the due date and what was requested): **Records Due** (**Records Deadlines** table, by the payer asking: the date the request names, else Medicare 45 days and others 30, _verify_) logs `records_requested` and opens **Send Records**, due on that date; sent logs `records_sent`.
- **Refund Overpayment** (`billing.refund-overpayment`, the cycle's `overpaid` step): **Read Credit Balance**, **Refund Due** (**Refund Deadlines** table: Medicare and Medicaid within 60 days of being identified, 42 CFR 401.305; patients 30 days) and **Approve Refund**, which needs `claims:approve`; approval reads the credit again and records a `refunded` event to whoever made the credit (the payer, or the patient, whose payment took the balance below zero, identified on the date it did), never more than they paid or than the credit balance (nothing when no credit is left), and keeping the credit closes the claim as paid. The step starts whenever the balance falls below zero: an 835 or a hand-posted payment that pays more than is owed is posted in full (its adjustment capped at what it left unpaid), leaving the credit to refund.
- **Patient Responsibility** (`billing.patient-responsibility`) runs in Bill Patient before each statement: **Read Patient Balance** returns the stored facts (balance, pickup state, date of service, last payer's plan type and kind, the claim filing indicators of the payers on the claim, the adjustments the last payer sent); the rule decides everything from them: it sums the last payer's PR adjustments as the cost share, marks the patient dual eligible when the claim has a Medicare payer and a Medicaid payer (Medicare and Medicaid Claim Filings tables), and takes the first balance-billing protection that applies: Medicare and Medicaid both on the claim (a QMB or Medicaid enrollee) blocks it, a Medicaid last payer caps it at the cost share Medicaid stated (42 CFR 447.15), Medicare caps it at the deductible and coinsurance, self-funded (ERISA) plans are exempt, and the example state rows cap fully insured plans at the in-network cost share in NH from 2026-01-01, OR from 2026-01-01 and AL from 2026-10-01 (all _verify_). **Protect Patient Balance** takes the protected amount off the balance as a `balance_protected` event with why; a blocked balance closes the claim with nothing billed.

## Deadlines and facilities

- **Watch Deadlines** runs every morning per agency: its Entry is a daily 06:00 schedule trigger, so the worker's schedule job (every 15 minutes) starts one run for each active agency once its own day (in the billing profile time zone, UTC without one) has reached 6:00, recorded in `schedule_runs` (agency, workflow, day) so a redelivered or retried job never starts a second run and one failing agency does not stop the others. Every date the billing nodes use as today (deadlines, invoice and appeal packet dates, refunds, filing days left, eligibility and claim status requests) is the agency's date from **Agency Today** and the billing profile time zone, and a date-only task due date is the end of that day there. **Read Deadlines** reads payers not filed yet (drafts included, a rejected submission not counting as filed) with their directory filing limit and claim filing indicator, each patient's last scheduled trip with a physician certification, open tasks with due dates and the reminders already opened; **Upcoming Deadlines** works out timely filing (Filing Limit: `filing_limit_days`, or the Federal Filing Limits table, 365 days for Medicare and TRICARE), the due dates of open appeal, records and refund tasks, and physician certifications expiring the PCS Valid Days (Check Limits, 60) after signing for patients whose last scheduled trip is within them, with the days left and whether a reminder was already opened (Dated Deadline), keeping those within the Look-Ahead Days (Deadline Limits, 90); **Deadline Action** takes the first action that applies, with the days from the Deadline Limits table: it raises a task due within the Task Due Soon Days (14) to priority 2 and within the Task Due Now Days (3) to 3, and opens a **Deadline Reminder** for timely filing within the Filing Reminder Days (30) or passed (after its last day) and certifications within the Certification Reminder Days (14), once per deadline, open or done (once per patient and certificate for certifications).
- **Facility invoicing**: a claim whose **Responsible Facility** is set (claim page, `claims.facility_id`; facilities under Admin) is on the `facility` step and waits; **Invoice Facilities** runs on the first of each month (in the agency's time zone) and issues one PDF per facility for the trips through last month with a balance that no invoice to that facility billed yet (`facility_invoice_claims`), so a trip assigned to a facility after its month was invoiced goes on the next, supplemental invoice (`facility_invoices.sequence`); each invoice is logged as `facility_invoiced` in each claim's files. A facility that is responsible for claims or has been invoiced cannot be deleted. The A/R aging report shows the facility as who owes the claim.

## Documents

**Add Document** (`billing.receive-document`, Start Task: Add Document) uploads a facesheet, PCS, signature form, ABN or MSP form (PDF, PNG, JPEG or TIFF) with its signed date; **Add Claim Document** stores it in S3 under `documents/<agency>/<claim>/`, keeps it in `claim_documents` and logs a `document` event, then **Record Document** reads it: **Document Facts** (by the kind of document) puts a PCS or ABN on file with its date or signs the release for billing, the patch signals the claim so its cycle looks again, and Check Claim runs. **Chase Document** opens a task due in the days the **Document Chase Days** table gives, takes the upload the same way (Add Claim Document, then Record Document) and asks again until a document of that kind is on file.

Chases also start on their own. While **Fix Claim** asks a biller to fix a blocked claim, it first runs **Chase Missing Documents** (`billing.chase-missing-documents`): **Document Chases** (`billing.document-chases`, a read through the `documents` store port) lists the documents open Chase Document runs on the claim are chasing (the kind each was started with, or the one a biller chose in Start document chase), **Documents to Chase** maps each issue to its document with **Issue Document** and the **Missing Document Issues** table (`pcs-missing` and `pcs-missing-medicare`: pcs, `signature-missing`: signature, `abn-missing`: abn), keeps each once and drops those already chased (**Chase Needed**), and one Chase Document run starts for each with its `kind`, skipping Start document chase. So a claim has at most one open chase per document; a chase a biller stopped starts again the next time Fix Claim finds the document missing. An agency chases more issues by adding rows to the table.
