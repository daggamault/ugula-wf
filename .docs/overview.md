# Overview

How Ugula works end to end: the workflow engine, the subworkflows billing is built from, tenancy and access, and the billing app from import to reports.

## The Workflow Engine

- **Graphs:** A workflow is a graph of nodes joined by **exec** wires (control flow) and **data** wires (typed values). Graphs are versioned and published; any graph can call another as a node, and a `Get Input` node reads a graph input next to the nodes that use it. The editor lays graphs out by their flow (loops never widen them) and can rearrange any graph.
- **Durable runs:** Runs persist their state in Postgres after every node with side effects (and every few pure steps), so they survive restarts without repeating work. A run can suspend for days while it waits on a human task, a timer, a signal (e.g. "this claim changed"), or child workflows, then resume where it left off. Signals are counted, so a run that was busy when one arrived still sees it when it next waits.
- **Starting runs:** A published workflow can be run from the browser with a form for its inputs. File inputs (`{ bucket, key }`) are an upload button: the file is stored under the agency's import area and the run receives its reference. Task fields of that type upload the same way, into the task's agency.
- **Human tasks:** Task nodes create tasks of a type (patient matching, PCR review, follow-ups, collections). Every run that works a claim is linked to it (`claim_runs`), so each task and stuck run shows on its claim; completing a task resumes its run on the chosen outcome.
- **Reliability:** Workers lease runs with fencing tokens, a sweeper recovers stalled runs, and transient failures retry while real faults stop the run for inspection and retry from the UI.
- **Scaling:** Workers scale horizontally. Postgres LISTEN/NOTIFY wakes an idle worker the moment a run is queued. Each worker claims runs only while it has a free slot (`WORKFLOW_CONCURRENCY`) and its event loop (`WORKER_MAX_EVENT_LOOP_UTILIZATION`) and memory (`WORKER_MAX_HEAP_MB`, 85% of the V8 heap limit by default, and `WORKER_MAX_RSS_MB`, unset by default) are under their limits; over a limit it finishes what it holds and claims nothing new until load falls back. Language-model calls share one cluster-wide limit (`COMPLETIONS_CONCURRENCY`), held as expiring leases in Redis, so adding workers never overloads the model server; a run that finds every lease taken gives up its slot and retries on a short timer. Task completions and signals are picked up before bulk work, and each import runs at most `WORKFLOW_CONCURRENCY` of its reports at once across the cluster, so one large file never takes every worker.
- **Separation:** The engine and its standard library (`libs/kernel/graph`) know nothing about billing. NEMSIS and billing nodes and models live in `libs/domain/nemsis` and `libs/domain/billing` and reach the database only through ports the worker implements.

## Subworkflows

Workflows are built from small, general nodes, so agencies can change billing logic without code:

- **Typed models:** a NEMSIS patient care report, its sections (patient, times, payment, scene, situation, disposition, medications and more), the claim, and the 837P claim are named models. Each model gets a **Break** node (one labelled output per field, such as `Last name · ePatient.02`) and a **Make** node (one input per field).
- **Tables:** a **Decision Table** checks rules top to bottom (is, is one of, starts with, at least, is empty and so on) and outputs the first matching rule's values, plus every rule that held as reasons. A **Lookup Table** maps codes to values. Both are edited as forms in the workflow editor.
- **Lists and logic:** Where, Pluck Field, Reshape Items, Make List, Sort By Field, Coalesce, Select, math and text nodes.
- **Capability nodes** do what a graph cannot: read and split NEMSIS files, match patients and payers, read narratives with the local model, price lines from fee schedules, save claims, run the claim cycle and render statements.

**Overrides:** every built-in graph can be overridden for a whole organization or for one agency. Override copies the graph and records the version it came from; once the copy is published, every workflow that uses that graph uses it, agency copy first, then the organization's, then the built-in graph. A copy must keep the same inputs, outputs and exits (its contract); when a built-in graph changes its contract, older copies stop applying until they are rebased. Compare shows a copy against the version it came from and the newest base. Each run pins the versions it uses when it starts, and child runs reuse their parent's, so publishing or removing an override never changes a run that has already started. See [.docs/overrides.md](overrides.md).

## Organizations, Agencies and Access

An organization (an EMS service or a billing company) has one or more agencies, and each agency owns its claims, patients, payers, fees and tasks. Users belong to one organization; owners see every agency, and everyone else has a role in each agency they work in. Roles are custom per agency, built from `resource:action` permissions, and seeded as Admin, Billing Manager, Biller and Viewer. Admins invite users with a one-time link; nobody can grant permissions they do not hold or remove an agency's last user admin. Agency pages live under `/agencies/:agencyId`, the agency picker in the sidebar switches agencies, and every API route checks membership and permissions. See [.docs/tenancy-and-access.md](tenancy-and-access.md).

## The Billing App

`billing.ingest-nemsis` starts one **Encounter to Claim** run per report. That run is made of smaller graphs, each one an override point: **stages** sequence the work, every billing decision is a small **rule** graph or a keyed **table** that returns its reasons, and each stage has an empty **Agency Rule** slot. Code nodes only read and write. See [.docs/billing-workflows.md](billing-workflows.md) for the catalog.

1. **Import:** NEMSIS 3.4 or 3.5 XML arrives by upload or SFTP and is split into one run per patient care report (PCR), read as a typed report, and `Open Draft Claim` opens its claim as a **Draft** straight away, before the patient is known, so every task the PCR needs is worked on that claim. NEMSIS records cities as USGS GNIS feature codes; the import names them from a `gnis_places` table the base seed loads, and keeps the code alongside. Element names and code descriptions come from `nemsis_elements` and `nemsis_codes`, built from the official 3.5 schema, so a report shows `2205001 Emergency Response (Primary Response Area)` rather than a bare code. `Map Encounter Facts` then turns the report into one typed snapshot, the **Encounter Facts** (trip, locations, patient, clinical, documentation, reported coverages), that every later rule reads instead of NEMSIS sections.
2. **Duplicates:** A PCR number is claimed once per agency. A re-imported or corrected report becomes a revision of its existing claim and goes to a biller instead of opening a second claim; voiding it from there works only while the claim has not gone to payers.
3. **Classification:** `Classify Trip` (the Classification table) decides from the dispositions (`eDisposition.12`, or `.27`, `.28` and `.30` in 3.5) and the type of service whether the trip is an emergency, scheduled, treat-no-transport, refusal or no-claim trip. Cancelled calls, calls with no patient contact and non-patient services (standby, rescue, crew or organ transport and the like) where nobody was transported are no-claim trips, which ask a biller before their draft is voided.
4. **Patient:** `Demographics From PCR` maps the report patient, which is matched to an existing patient only on the same last name, birth date and first name or nickname. One exact match is used and no close match creates the patient. Likely matches (similar names found by trigram search and Jaro-Winkler, birth date typos) go to a `Confirm patient` task that only asks the biller to use the preselected candidate or create a new patient from the report. A report missing the name or birth date asks for just those first. Once the patient is known, `Assign Patient` sets it on the draft claim.
5. **Payers:** `Determine Payers` takes the insurances `Coverages From PCR` maps, or Medicare or Medicaid from the payment method. The `Medicare Secondary Payer` rule reads the MSP answers (employer plan, ESRD, disability, accident or work injury; the accident answer is prefilled from a work-related injury, workers compensation or a transport accident on the PCR, the rest are entered on the claim data tab) and puts Medicare after the payer that pays first. Their names link to the payer directory by name or by a name a biller already matched. Other names are compared with the directory by embedding (pgvector), the local language model suggests the likely payer, and a biller confirms it once (one task per name, however often the report repeats it); that name then links automatically. `Coordination Order` bills them in the priority the report gives (Coverage Priority table).
6. **Service:** the local language model lists the medication doses and CMS ALS2 procedures the narrative documents, each with the words that show it; a finding the narrative does not contain, or a procedure its quote does not name, is dropped, and IV solutions (saline, Ringer's, dextrose) are never medications. `Determine Service` runs the rule for the classification (`Emergency Trip`, `Scheduled Trip`, `Treat, No Transport`, `Refusal`), built on the `Level of Service`, `Emergency Status` and `Loaded Miles` rules and tables over the level of care, CMS service level, the ALS assessment, coded IV/IO medications other than IV solutions (RxNorm), coded ALS2 procedures (SNOMED CT), response mode and odometers. SCT is only for interfacility transports, and a trip is an emergency when the unit responded immediately (emergent, including when later downgraded), so an emergent interfacility transfer is billed as one; the crew's CMS service level counts only when no response mode was reported. `Review PCR` shows the biller the complaint, symptom, vitals, coded procedures and what the report documents for billing, and warns when no vitals support medical necessity. A patient pronounced dead after the ambulance was called and before loading, whether before or after it arrived (`Deceased Handling`: dead at the scene, with or without the body then transported, or expired in the field and not transported), is billed at the BLS base rate with QL and no mileage, as CMS pays it (Medicare Benefit Policy Manual ch. 10 §10.2.6; QL is "patient pronounced dead after ambulance called"); a death pronounced before dispatch is not billable and one after loading (including resuscitation that went on into the ED) is billed as the service furnished, and miles past the closest hospital (ePayment.48) when the patient chose a farther facility (transport reason B or C) are billed on their own A0888 line with GY (`Non-Covered Miles`). A biller confirms it, or holds the report (then releases or voids it); correcting the loaded miles there recalculates the non-covered miles.
7. **Claim:** `Assign Charges` turns the confirmed service into HCPCS lines (`Base Rate Code`: a base rate by classification, level and emergency, A0998 for no transport; `Mileage Lines`: A0425 loaded miles rounded up to the tenth, or to the whole mile from 100 miles), priced by `Price Precedence` (a price set for the claim, else the primary payer's fee schedule, else the default). At 837P time `Line Modifiers` gives each line its modifiers: the origin/destination letters or QL, GM when several patients rode on the trip, GY, GA (an ABN on file for a non-emergency Medicare trip) or GZ (a denial expected with no ABN), and GY on A0888; `Narrative Note` sends an 80-character medical necessity summary (NTE*ADD) when the claim needs one, `Admission Date` sends DTP*435 when known, and the prior authorization UTN goes on REF*G1. Checks also cover the MSP answers and payer order, the ABN, prior authorization for repetitive scheduled Medicare trips past the third round trip and its expiry, and facility responsibility. Documents (facesheet, PCS, signature form, ABN, MSP form) are uploaded with an `Add Document` task (or on the chase task once it arrives), stored in S3, and `Receive Document` records what each documents and checks the claim again; `Chase Document` opens a task with a due date for a missing one. `Assign Claim Properties` fills the claim from the facts, including `Assign Diagnoses`, `Origin/Destination Modifiers`, the `Transport Reason` and documentation: the release-for-billing signature (signed, a Medicare exception because the patient could not sign, refused or missing), the physician certification statement, the CMS transport reason (reported, else from the reason for the destination), ambulance conditions, prior authorization, weight and trip times. `Check Claim` runs the check rules (`Check Billing Signature`, `Check Physician Certification`, `Check Transport Reason`, `Check Mileage`, `Check Timely Filing` and more): a claim cannot go to a payer without a billing signature or a documented exception, a transport reason on transports (a patient pronounced dead before loading was not transported), a certification on scheduled non-emergency Medicare trips, or an MSP answer when Medicare is billed after another payer (SBR05); billing only the patient skips the payer-only checks (signature, certification, ABN, MSP, prior authorization, facility, filing); old certifications, out-of-order times and nearing or passed filing limits are warnings. Each issue has a code whose severity (blocking, warning or off) comes from the agency's **Check Severity** table. An incomplete claim stays in Draft and goes to a biller; edits that change the classification, service, miles or payers reprice it (`Reprice Triggers`); a valid one is saved and moves to **Needs review**. A held or incomplete PCR that a biller voids closes its draft as **Void**.
8. **Claim cycle:** Each claim gets its own long-running workflow that sleeps until a claim change or a deadline, and works through its payers in order. `Read Claim Ledger` reads where the claim stands, the `Next Claim Step` rule decides the next step (Claim Steps table) under the agency's **Claim Policy** table (waits, statements, collections threshold, write-off limit and review, per kind of payer), and `Record Claim Step` records it as the claim's status, so the status a biller filters by is always the step the claim is on. Review and submission run `Check Claim` first.
   - **Needs review:** before each payer, a `Review claim` task makes a biller check and approve the claim; nothing goes to a clearinghouse unreviewed, including resubmissions;
   - **Ready to submit:** as soon as the review is approved, the payer cycle files the claim on its own as an **837P file** (`Prepare 837P Claim`, `Map 837P Claim`, `File 837P Claim`), logs it submitted, and `Send 837P to Clearinghouse` uploads it through the agency's clearinghouse connection (without one, the file waits on the claim for the biller to upload). The `Map 837P Claim` graph maps the claim (subscriber, payer, ambulance conditions, modifiers, service lines), and the file only serializes what it maps. When the file cannot be created (an incomplete billing profile, blocking claim data, an incomplete mapping or used-up control numbers), a `Claim could not be filed` task says why and lets the biller try again, fix the data (which sends it back to review), skip the payer or mark it submitted another way;
   - **Submitted:** a TA1, 999 or 277CA rejection sends the claim back to review with the reason (a TA1 envelope rejection also asks for the clearinghouse setup to be fixed); a payer that hasn't answered in 30 days gets a claim status request (276, real time or batch) and a follow-up task showing its latest status (**Needs follow-up**: resubmit, keep waiting, or move to the next payer);
   - **Reconcile payment:** a payer payment posted against the claim that leaves a balance opens a reconcile task (continue to the next payer or the patient, or write off the rest); a payment that settles the claim closes it as paid;
   - **Denied:** a denial the Remittance Routing table routes to `denial`, `appeal` or `fix` (by CARC) starts `Work Denial`: the `Denial Category` rule suggests what it needs and a `Denial decision` task corrects the claim (`Correct Claim`: the `Replacement or Reopening` rule, by the payer's **Corrections** setting, queues a replacement filed with CLM05-3 = 7 and REF*F8, files a frequency 8 void, or asks for a Medicare reopening), appeals it (`Appeal Claim`: the `Appeal Level and Deadline` rule, redetermination within 120 days of the remittance and reconsideration within 180 for Medicare, others by the payer's **Appeal Limit**; an appeal packet PDF with the claim summary, the PCR and the PDFs on the claim; a `Send appeal` task due on the deadline; then a wait for the decision, an overdue task and the decision on the ledger), bills another payer, moves the balance to the patient or writes it off;
   - **Credit balance:** a balance below zero (an overpayment posts in full, its adjustment capped at what it left unpaid) starts `Refund Overpayment`: the `Refund Due` rule (Medicare and Medicaid within 60 days) and an `Approve refund` task that needs the `claims:approve` permission record the refund on the ledger; write-offs above the Claim Policy approval threshold and collections placements need the same approval;
   - **Patient balance:** once all payers are done, the `Patient Responsibility` rule (Balance-Billing Protection table by state, plan type and date of service; Medicaid never balance billed, Medicare capped at its cost share, example state rows to verify) takes what the patient may not be billed off the balance with why, then up to three patient statements (PDFs) go out 30 days apart;
   - **Facility:** a claim whose responsible facility is set waits for the facility, which `Invoice Facilities` bills on one PDF invoice a month. At intake the `Facility Responsibility` rule decides it from the facility directory (a contract facility at the pickup or destination) and the facility stay a biller confirms (a hospital inpatient who stays admitted, a SNF Part A stay on a non-emergency trip), and a `Bill facility` task names the facility (also when a biller's answer at Fix Claim makes a facility responsible); a facility that has not paid `facilityWaitDays` (Claim Policy, 60 by default) after its invoice opens a `Follow up with facility` task (keep waiting, write off or send to collections); a 271 that reports an inpatient or SNF stay on the date of service is a warning to confirm;
   - **Balance review:** an unpaid balance after that goes to a biller; claims close as **Paid**, **Written off**, **Sent to collections** or **Void**.
   - **Deadlines:** `Watch Deadlines` runs every morning for every agency (a pg-boss schedule like the clearinghouse poll) and raises appeal, records request and refund tasks as they come due, and opens reminders for timely filing (drafts included) and expiring physician certifications, once per deadline. A payer request for records is logged with a `Log Records Request` task, which then asks for the records by their due date.
9. **Payer files:** the worker polls the clearinghouse SFTP download folders, routes each file to the agency it is addressed to (ISA08 is the agency's submitter ID) and starts `Receive Payer File` for it (a file uploaded by hand on Payer Files starts the same workflow), which applies it and starts `Review Payer File Line` (a task on the claim) for every line a biller has to look at. Each claim lists the payer files that touched it. An 835 posts each claim's payment, contractual adjustments and reason codes (patient responsibility stays on the balance), matched by claim number and payer, as `Route Remittance` decides (`Classify Adjustments` with the Adjustment Classes table, then the Remittance Routing table; reversals, takebacks and payers not on the claim go to a biller unposted, and a provider-level adjustment (PLB) becomes a line to post by hand); a TA1 rejects the envelope of its 837P file; a 999 accepts or rejects every claim in its 837P file; a 277CA accepts or rejects single claims; a 277 claim status is logged in each claim's History; a 271 records whether each payer says the coverage is active (an inactive coverage blocks billing that payer, and a Medicare answer naming a Medicare Advantage plan asks a biller to bill that plan instead). `Check Eligibility` runs when a claim's payers are saved and from Start Task on the claim: a real-time 270 when the connection supports it, else a batch 270. Each 270 costs money, so a payer already answered or waiting for a batch answer is not asked again, an answer from another claim of the patient with the same payer and member ID in the same month of service is reused, an unreadable real-time answer is not re-sent in batch, and changing a payer or member ID clears the old answer; the claim page button always asks; the claim page can also download the 270. Every line keeps its outcome, unclear lines (reversals, unknown claims, payers not on the claim) go to a biller, and the same file is never applied twice.
10. **Admin:** Users and Roles, Payers (the directory, with each clearinghouse payer ID, its filing limit, how it takes corrections, its appeal limit, its plan type and the report names it has learned), Facilities (who is invoiced for the trips they are responsible for; the A/R aging report shows them), Fees, and Settings (the agency's billing profile, clearinghouse IDs and clearinghouse connection) drive the 837P files and statements.
11. **Working it:** Claims run in the background; billers work **Tasks**, small decisions that keep many claims moving without anyone owning a claim. The Tasks list is the work queue, by queue and assignee, and Next Task moves through it. A task page holds what its decision needs (the issue, then Claim, Encounter and Patient tabs that flag where the claim differs from the PCR, and options that each say what they do) and links its claim only as a reference. **Claims** is the record: Search finds any claim, open or closed, by first and last name, birth date or any of the three numbers, all in SQL, and a claim's page is a read-only record of where it stands and the task it is waiting on. Its **Start Task** menu is how a biller changes a claim: `Correct Claim Data`, `Change Payers`, `Set Responsible Facility`, `Add Document`, `Chase Document`, `Log Records Request` and `Post Payment` each open a task for that claim and go straight to it, and Check Eligibility and Restart Payer Cycle run from the same menu. Closing a claim cancels its other runs, including its payer cycle and open claim tasks. Claims and patients get sequential numbers (`claims.number`, `patients.number`, identity columns shared across agencies), and the encounter number is the PCR number. Each claim has Overview, Claim data and History tabs, and its Files list the source encounter (NEMSIS XML), its 837P files and statements. Patients searches by name and birth date; each import lists what every PCR in the file became. New tasks, stuck runs and every message a biller sees are kept in the notification bell, stored per agency and user so they follow the biller across devices.
12. **Reports:** Every import, report, claim line, coverage, diagnosis and ledger event is a relational row, so A/R aging, monthly collections, payer performance and HCPCS charges are plain SQL. Reports lists them; each one opens an options page (dates of service, where the report uses them) and then a results page that pages at 100 rows, prints the current page as a black and gray document, and downloads as CSV.
