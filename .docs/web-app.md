# Web App

React app in `apps/web`, built with Vite. Pages live in `src/features/<area>`; shared building blocks in `src/shared`.

## Routing

- A small router (`src/shared/router.tsx`) keeps all app state in the URL.
- Agency pages live under `/agencies/:agencyId/...`. Code links to agency-relative paths (`/claims/123`); `navigate`, `Link` and `useLocation` add and strip the prefix, so features never handle agency IDs.
- Editing pages call `useUnsavedChanges(dirty)` while their form differs from what was loaded. Leaving for another page (links, `navigate`, back and forward) then asks to discard the changes in the one `UnsavedChangesDialog` the workspace mounts, and reload or close asks the browser to confirm. Query-only changes (panels, tabs) pass unless the page names the params that identify it (`['version']` in the workflow and table editors). Navigations after a successful save or delete pass `{ force: true }`.
- Public pages: `/invitation?token=…` and `/password?token=…`.
- `App` → `AuthGate` (sign in) → `AgencyGate` (pick and load the agency's access) → `Workspace` (shell, navigation, pages).

## API calls

`createApi` rewrites `/api/...` to `/api/agencies/:agencyId/...` for the agency in the URL, except auth and the agency list. Feature clients call plain paths like `/api/claims`.

## Access in components

- `AccessProvider` holds the loaded `Access` (agency, organization, permissions).
- `useCan()('users:update')` decides whether to show an action; navigation items declare the permission they need.
- The API enforces the same rules, so hidden is never the only protection.

## Live updates

`createLive(sseUrl, { agencyId })` opens `/events?agency=<id>` on the SSE app; pages reload their data on matching events and on reconnect.

## Lists

Lists search, sort, filter and page on the server, with the state in the URL (`useSearchState`, `useTableState` in `shared/url-state.ts`). A list's spec names its filterable columns (`filters: ['kind', 'scope']`); each is a comma list in the URL (`?kind=node&scope=agency,system`) that the list sends to its endpoint as is. A spec can default a filter (`defaults: { kind: ['workflow'] }`): it applies while the URL leaves the column out, and clearing it writes an empty value (`?kind=`) so the list shows everything. The endpoint answers with the page and its `facets`: for each filterable column, the values in the database with their counts, each counted under the search and every other column's filter (`facetCounts` and `whereFacets` in the API's `shared/facets.ts`). `Search` shows one button per filterable column above the table (`ColumnFilters`), the same on every screen size since phones show rows as cards without a header; it opens a popover of checkboxes with counts, a find box once there are many values, and Clear. Filters that match nothing offer **Clear Filters**.

## Tasks, imports and claims

Billers work tasks. `/tasks` is the work queue (by queue and assignee, Next Task moves through it). A task page (`/tasks/:id`) leads with its title, subject and summary and **Your Decision** in one card: each option is a sentence saying what it does (`hints` on `std.human.task`, else a fallback for the few outcomes that mean one thing everywhere) above its button, with the options separated by "or"; a field only one outcome requires (such as the patient Choose the Patient needs for Same) sits with that option, and the other fields sit above them all. When the task's `prefill` is `current`, each edited field shows what it changed from (with Undo). After a decision, Done replaces the options. Below the card, what the workflow passed shows as **Workflow Details**. A task field with a `codeSet` (such as `icd10cm`) is a code picker: one searchable list that queries `GET /api/codes` by code or description, suggests the codes of its `codeList` (a NEMSIS pick list) before anything is typed, and shows every option as Description (code).

An import page (`/imports/:id`) shows how many PCRs the file held and how many became new, revised and unchanged encounters, the claims made and their charges, and a row per PCR with its encounter, patient, outcome and claim. Uploading a file links to its import.

The claim page (`/claims/:id`) is a read-only record of a claim that needs review. **Overview** shows the summary (total, classification, level of service, loaded miles), the **Review** (status, revision, and who approved or held it, when and why, or that it waits for a biller), every reason the workflows gave, the encounter it bills (PCR number and revision, times, pickup and destination, narrative, a link to its import), the charge lines with their modifiers, and the payers. **Claim Data** shows the date of service, diagnoses, the origin and destination modifier, the transport reason, condition codes and patient weight, and the patient's birth date and address. Every code shows as Description (code) from the `codes` table.

## Workflow editor

- A workflow's start node has a **Trigger** section (`trigger-editor.tsx`): when someone runs it, on an event (from `WorkflowEventsContext`, with conditions on its fields) or on a schedule. The canvas titles the start node by it (Start, On Encounter Created, On Schedule), the Workflows list shows it under **Starts**, and a run page names the event that started the run.
- `/workflows` lists workflows by default; its filters are **Kind** (Workflow, Subworkflow; `?kind=` shows both) and **Scope** (Standard, Custom; `?scope=`), so custom subworkflows are `?kind=node&scope=agency`. **New Workflow** becomes **New Subworkflow** while the list shows only subworkflows.
- `?panel=signature` opens **Inputs and Outputs** (`workflow-panel.tsx`): inputs, outputs, exits and variables as reorderable rows with one friendly **Name**, a description and the shared `TypePicker`, plus Add Get and Add Set per variable (`signature-edits.ts`). A name is committed on blur or Enter and refused when blank or taken. It becomes the camelCase key while nothing in the graph uses the pin, and otherwise only its `label`, so wires, Input nodes, Return values and callers keep working; an input an event fills in by name, and an exit a Return finishes through, always keep their key. A variable follows the same rule: its key and its Get and Set nodes follow the name unless an expression uses it, which keeps the key and stores a `label`. Keys never clash with the exec pins they share a namespace with (outputs with exits, inputs with the exec input). Removing an input also removes its Get Input nodes, removing an output the values Return nodes hold for it, and removing a variable its Get and Set nodes (`setPins`, `setVariables`). Changing a type, removing a pin or turning Runs as a Step off disconnects only the wires that change broke and says how many (undo restores them). Inputs have **Required**, or a **When Not Given** default; an event-triggered workflow offers the event's payload fields as one-click inputs. Only an agency's custom draft edits it; built-ins, copies (the contract is fixed) and published versions show it read-only with the reason. `?panel=compare` opens the compare panel of a copy; `?removed=shown` adds the base's removed nodes as ghosts; `?inside={node}` shows a std composite read-only over the canvas (double-click it), while published subworkflows open as their own page. Documentation hints from `documentationIssues` show as a collapsible warning.
- The canvas (`shared/graph`) works like Unreal Blueprints. Node headers are tinted by kind (`catalog.kindOf`: entry, action, pure, flow, human task, table, subworkflow; `node-*` tokens), show `summaryOf` under the title (the description is the tooltip), label exits, and draw exec pins as solid triangles. Break and Make nodes show only wired, bound or revealed fields; **Add Field** reveals one by adding it to the instance's UI-only `shown` list, which the engine ignores. On a custom draft, Return shows an **Add Output** pin and Entry an **Add Input** pin (`NEW_PIN`): dropping a data wire on one adds a workflow output or input named, typed and described after the other end and wires it (`connect`), so the signature grows from the canvas. Right-clicking or double-clicking one of their data pins opens a small menu to rename the pin, open its type and details in Inputs and Outputs, or remove it with its wires (`signature-edits.ts`: `renamePinNamed`, `removePin`). Dragging off a record pin into empty space offers that record's fields first (`pickerEntries`, `record-fields.ts`); each is a std Get Field set to the field, titled by the field's model label (**Charge Lines**, summary **From Claim**, labels by `catalog`), and dragging off a list offers **For Each** first. Layout sizes Break and Make nodes by the pins they show. A node's note shows under its header. A Constant of codes and an Equal or Not Equal testing a fixed code list each code with its meaning through `CodeLabel`, from `GET /api/codes/kind` (a NEMSIS code from the element its kind comes from, `codeKindElements`; ICD-10, RxNorm, SNOMED, HCPCS and modifiers from `codes`; classifications and place letters from their labels), looked up once per agency (`code-meanings.ts`). A reroute (`std.flow.reroute`) is a small knot. Comments (`def.comments`) are tinted, resizable frames behind the nodes that carry the nodes inside them.
- Adding nodes: dragging a wire to empty space, right-clicking the canvas, pressing A, or **Add Node** opens the picker popover (`node-picker.tsx`) at that spot. It searches titles, descriptions, categories and keywords, shows Basic nodes unless **Show Advanced** is on (kept in `localStorage`), and from a pin lists only nodes with a compatible pin (`compatibleEntries`, default-config signatures), then places and wires the new node (`addWired`).
- Edits go through a capped undo history of `GraphDef` snapshots (`history.ts`); edits within 600ms, such as typing, are one step. Copy and paste use the system clipboard as a validated JSON clip (`clipboard.ts`), so nodes move between graphs with fresh ids and their inner wires.
- Keyboard and mouse: Ctrl/Cmd+Z undo; Ctrl/Cmd+Shift+Z or Ctrl+Y redo; Ctrl/Cmd+C, V and D copy, paste and duplicate; Delete or Backspace removes the selection (a comment's nodes stay); C frames the selection in a comment; A or right-click opens the picker; Shift-drag box-selects and Ctrl/Cmd-click adds to the selection; Alt+click a wire or pin disconnects it; double-click a wire adds a reroute knot; double-click a subworkflow opens it.
- On a copy the editor diffs the definition against `compare().copiedFrom` by node id (`override-diff.ts`) and passes `changes`, `changedEdges` and `removed` to the canvas; nodes whose subworkflow (`GET /graphs/nodes` `overridden`) or table (`GET /tables/effective`) is customized get the same outline.
- `custom` is the accent for anything an agency changed; see [Overrides](overrides.md).
- The node inspector reads top to bottom: what the node does, Inputs (wired ones read "From {Node} · {Pin}"), Settings, Outputs and Then (exit docs from the node definition), then collapsed **Rename and Note** and **Advanced** (retry in seconds, settings as JSON).
- Settings never start as JSON. `SETTINGS_EDITORS` (`node-settings.tsx`) maps node types to dedicated editors: tables, formulas (`std.expr` and the list formula nodes, checked live with `exprProblem`, inputs from `freeIdentifiers`, functions from `exprFunctionDocs`), Human Task, Make and Break Record fields, the workflow nodes (a picker over published workflows and versions), Constant, To Code, variables and Get Input. Every other node gets `ConfigForm`, built from its valibot config schema (`config-schema.ts`): text, numbers with bounds, booleans, picklists and literal unions, lists, records, value types (`TypePicker`: one searchable list grouped into Basics, Records by model title, IDs, Codes and an advanced Custom Record with its own fields, plus a **List** checkbox; `Select` options can carry a `group` heading), any value and field choices; a shape it cannot read falls back to JSON for that setting only.
- `ValueField` edits records field by field and lists row by row; only open records and `any` values (behind **Kind of Value: JSON**) are JSON. Expression bindings are checked against the graph's variables, the only names the engine gives them.

UI rules (tokens, spacing, controls, accessibility) are in [Standards](standards.md).

Adding a facility (Settings, Facilities) can fill its name, address, phone and kind from the CMS hospital list: **Fill From CMS Hospital** searches `GET /api/facilities/hospitals` by name.
