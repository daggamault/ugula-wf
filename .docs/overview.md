# Overview

How Ugula works end to end: the workflow engine, the graphs billing is built from, tenancy and access, and the billing app from a NEMSIS file to a claim that needs review.

## The Workflow Engine

- **Graphs:** A workflow is a graph of nodes joined by **exec** wires (control flow) and **data** wires (typed values). Graphs are versioned and published; any graph can call another as a node, and a `Get Input` node reads a graph input next to the nodes that use it. The editor lays graphs out by their flow (loops never widen them) and can rearrange any graph.
- **Durable runs:** Runs persist their state in Postgres after every node with side effects (and every few pure steps), so they survive restarts without repeating work. A run can suspend for days while it waits on a human task, a timer, a signal or child workflows, then resume where it left off. Signals are counted, so a run that was busy when one arrived still sees it when it next waits.
- **Triggers and events:** A workflow's start node says what starts it: someone running it, an event (a PCR file received, an encounter created or revised, a claim created, a task completed, with conditions on the event's fields) or a schedule, and the canvas titles it by that trigger (On Encounter Created). Events are written to an outbox in the same transaction as the change, and the worker starts every published workflow whose trigger matches, so an agency adds its own reaction to an event without overriding a built-in workflow. See [Workflow Engine](workflow-engine.md#triggers-and-events).
- **Starting runs:** A published workflow can be run from the browser with a form for its inputs. File inputs (`{ bucket, key }`) are an upload button: the file is stored under the agency's import area and the run receives its reference. Task fields of that type upload the same way, into the task's agency.
- **Human tasks:** Task nodes create tasks in a queue (choose a patient, complete a patient, match a payer); completing a task resumes its run on the chosen outcome.
- **Reliability:** Workers lease runs with fencing tokens, a sweeper recovers stalled runs, and transient failures retry while real faults stop the run for inspection and retry from the UI.
- **Scaling:** Workers scale horizontally. Postgres LISTEN/NOTIFY wakes an idle worker the moment a run is queued. Each worker claims runs only while it has a free slot (`WORKER_RUN_CONCURRENCY`) and its event loop (`WORKER_MAX_EVENT_LOOP_UTILIZATION`) and memory (`WORKER_MAX_HEAP_MB`, 85% of the V8 heap limit by default, and `WORKER_MAX_RSS_MB`, unset by default) are under their limits; over a limit it finishes what it holds and claims nothing new until load falls back. Task completions and signals are picked up before bulk work.
- **Separation:** The engine and its standard library (`libs/kernel/graph`) know nothing about billing. NEMSIS and billing nodes and records live in `libs/domain/nemsis` and `libs/domain/billing` and reach the database only through ports the worker implements.

## Graphs From Primitives

Billing is drawn from small, general nodes, so agencies can read and change billing logic without code. [Workflows](workflows.md) is the design and the catalog.

- **Records:** the Encounter (one patient care report in billing terms), its parts (Person, Address, Scene, Destination, Times, Odometer, Payment, Insurance, Medication, Procedure, Vital Signs, Signature, Crew Member, Attachment) and the Claim, Coverage and Charge Line. Each record has a **Break** node (one Title Case output per field, such as **Last Name**, described with its NEMSIS element) and a **Make** node (one input per field); a field that holds another record is a typed pin you Break again, and a NEMSIS coded field is typed by its code set (Incident Disposition Code, Service Type Code), so it only connects where that code set is expected.
- **Primitives:** Constant (such as a list of codes), Contains, Equal, comparisons, Is Null, And, Or and Not, Select and Choose Value, math, text, time, lists (Keep Items Where, Run Rule for Each, Sort by Field, Pluck Field), Lookup and Decision Tables, Branch, For Each, variables and Try. A generic primitive takes the type of the first typed wire connected to it, so a wrong pin cannot connect after it.
- **Services** do what a graph cannot: Read PCR File, Read PCR, Save Encounter, Read Encounter, Find Patient, Save Patient, Find Payer, Find Fee, Check Diagnoses, Search Diagnoses and Save Claim.
- **Tables** hold reference data only (code mappings); code lists are Constants inside the rule that reads them, and every decision is drawn on the canvas.

**Overrides:** every built-in graph and shared table can be customized for one agency; organizations own agencies but no workflows. Customizing copies the graph and records the version it came from; once the copy is published, every workflow in that agency that uses that graph uses it instead of the built-in graph. A copy must keep the same inputs, outputs and exits (its contract); when a built-in graph changes its contract, older copies stop applying until they are rebased. Compare shows a copy against the version it came from and the newest base. Each run pins the versions it uses when it starts, and child runs reuse their parent's, so publishing or removing an override never changes a run that has already started. See [Overrides](overrides.md).

## Organizations, Agencies and Access

An organization (an EMS service or a billing company) has one or more agencies, and each agency owns its encounters, claims, patients, payers, fees and tasks. Users belong to one organization; owners see every agency, and everyone else has a role in each agency they work in. Roles are custom per agency, built from `resource:action` permissions, and seeded as Admin, Billing Manager, Biller and Viewer. Admins invite users with a one-time link; nobody can grant permissions they do not hold or remove an agency's last user admin. Agency pages live under `/agencies/:agencyId`, the agency picker in the sidebar switches agencies, and every API route checks membership and permissions. See [Tenancy and Access](tenancy-and-access.md).

## The Billing App

Today the app covers one path: a NEMSIS file in, claims that need review out. Everything later in a claim's life (eligibility, checks, submission, remittance, denials, patient balances) is rebuilt on the same records and primitives next.

1. **Import:** NEMSIS 3.4 or 3.5 XML arrives by upload or SFTP. The API records the import and emits `pcr_file.received` in one transaction, and refuses the file when no published workflow starts on it. **Import PCR File** stores each patient care report, reads it as an Encounter (city codes named from `gnis_places`, attached files stored on their own) and saves it by its PCR number: new, revised (a changed copy raises the revision) or unchanged. A report that cannot be saved is counted as failed and the rest go on. Each import lists what every PCR in it became.
2. **Encounter to claim:** saving a new encounter emits `encounter.created`, which starts **Encounter to Claim**; a revised one emits `encounter.revised`, which starts **Revised Encounter to Claim**. Both run **Build Claim**:
   - **Classification:** Trip Classification runs six criteria rules (Not Billable, Refusal, Pronounced Dead, No Transport, Transport and Scheduled Criteria), each a few code lists tested against the dispositions, arrest outcome and type of service, and takes the first kind of trip that holds (not billable, refusal, pronounced dead before loading, treated without transport, scheduled, emergency), with every reason. A trip that is not billed makes no claim.
   - **Patient:** Find Patient matches the patient by last name, birth date and first name or nickname; one exact match is used and no match adds the patient. Similar patients go to a Choose the Patient task, and a report without a name or birth date to a Complete the Patient task.
   - **Service:** Service Details gives Level of Service (the highest of the SCT, ALS2 and ALS1 Criteria that holds, else BLS, from ALS2 procedures and IV/IO medications this unit gave, counted per item, the ALS assessment and the crew's level), Emergency Status (the response urgency, else the response mode, else the call type or crew level), Loaded Miles (rounded up to the tenth under 100 miles, to the whole mile from 100) and the Service Date; Diagnoses takes the impressions, then the symptoms; Origin and Destination gives the modifier letters from Origin Letter and the Destination Letters table.
   - **Payers:** Billing Order ranks the reported insurances, workers' compensation, auto and liability payers before Medicare; Payer Checks flags Medicare billed first on a work injury, transport accident or treatment without transport, and an insurer payment method with no insurance reported; Resolve Coverage finds each in the payer directory by name or a linked name, or asks a biller to Match the Payer among similar names, and codes the relationship to the insured.
   - **Charges:** Charge Lines gives the base rate (A0998 without transport, else the Base Rate Codes table by aircraft or by ground level, BLS when pronounced dead) and the mileage code of the vehicle for covered miles, with A0888 for miles beyond the closest facility when the patient chose a farther one, each with the Line Modifiers (origin and destination, QL, GM); Price Line prices each from the payer's fee or the agency's standard fee.
   - **Checks:** Claim Checks flags a missing signed release for billing (or the signature exception without a facility signature), a missing or stale physician certification on a non-emergency transport, a dialysis transport without prior authorization, and a claim past timely filing.
   - **Claim:** Save Claim saves it as **Needs Review**, with every reason, and emits `claim.created`; a revised encounter replaces its claim as a new revision that needs review again.
   - **Review:** every claim ends on a biller's review, as the law requires: Review Claim gives a Review the Claim task that only a user with `claims:approve` can complete. Approved claims are ready for the clearinghouse; held claims keep a note saying why. A decision counts only for the revision the biller saw, and replacing a claim cancels the review still open on its earlier revision.
3. **Working it:** Billers work **Tasks**, small decisions that keep encounters moving. **Claims** lists and searches claims by name, birth date or any number; a claim's page shows its decisions and reasons, patient, payers, charge lines with modifiers, diagnoses and the encounter it bills. Patients, Payers, Facilities, Fees and Settings hold the agency's data. New tasks, stuck runs and messages are kept in the notification bell.
